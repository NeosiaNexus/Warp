# Analyse architecturale de Minestom et projets de reference pour Warp

**Date** : 31 mars 2026
**Objectif** : Extraire les patterns architecturaux de Minestom (et autres projets MC from-scratch) applicables a un proxy Minecraft (Warp vs Velocity)
**Sources** : GitHub Minestom, documentation officielle, Javadoc, Pumpkin MC, Krypton, Velocity

---

## SYNTHESE EXECUTIVE

Minestom a prouve qu'un projet Java from-scratch peut surpasser l'incumbent (Paper/Spigot) sur les axes performance, maintenabilite et extensibilite. Les patterns cles transposables a Warp sont :

| Pattern | Applicabilite Proxy | Priorite |
|---------|---------------------|----------|
| Packets comme records immutables + sealed interfaces | DIRECTE | P0 |
| Event node tree hierarchique | DIRECTE (avec adaptation) | P0 |
| Separation API/Implementation | DIRECTE | P0 |
| Code generation pour les registries | DIRECTE (packets MC) | P1 |
| Extension system avec ClassLoader isole | DIRECTE | P1 |
| NetworkBuffer zero-copy | ADAPTEE (blind forwarding) | P0 |
| Acquirable API (thread-safety) | NON APPLICABLE (proxy != tick-based) | - |
| ThreadDispatcher par chunks | NON APPLICABLE | - |

## 1. STRUCTURE DU PROJET MINESTOM

### 1.1 Organisation generale

Minestom est un projet Gradle **mono-module** (avec sous-projets pour tests/demos) :

```
Minestom/
├── build-src/              # Plugins Gradle custom (minestom.*.gradle.kts)
├── code-generators/        # Generation de code depuis les registries MC
├── demo/                   # Application de demonstration
├── jcstress-tests/         # Tests de concurrence
├── jmh-benchmarks/         # Benchmarks de performance
├── src/
│   ├── autogenerated/      # Code genere (blocks, items, entities, sounds...)
│   └── main/java/net/minestom/server/
│       ├── adventure/      # Serialisation de text components
│       ├── codec/          # Encodage/decodage (JSON, NBT)
│       ├── collision/      # Physique, bounding boxes
│       ├── command/        # Framework de commandes (Brigadier)
│       ├── entity/         # Entites, attributs, metadata
│       ├── event/          # Systeme d'evenements (EventNode)
│       ├── instance/       # Mondes, chunks, blocs, lighting
│       ├── item/           # Items, enchantements
│       ├── network/        # Paquets et protocole
│       ├── recipe/         # Recettes
│       ├── thread/         # ThreadDispatcher, Acquirable
│       └── world/          # Dimensions, biomes
├── build.gradle.kts
└── settings.gradle.kts
```

### 1.2 Conventions de nommage

- **Package** : `net.minestom.server.*` (reverse DNS)
- **Suffixes de classes** : `Manager`, `Handler`, `Provider`, `Registry`, `Impl`
- **Registries generes** : noms au pluriel (`Blocks`, `Materials`, `EntityTypes`)
- **Fichiers** : PascalCase pour les classes

### 1.3 Lecons pour Warp

**APPLICABLE** : La structure mono-module est trop limitante pour un proxy. Velocity utilise 3 modules (`api/`, `proxy/`, `native/`), Pumpkin utilise 8 crates. Krypton a aussi une separation `api/` / `server/`.

**Recommandation Warp** : Structure multi-module des le depart :

```
warp/
├── warp-api/           # Interfaces publiques pour les plugins
├── warp-protocol/      # Packets, codecs, NetworkBuffer
├── warp-proxy/         # Implementation du proxy
├── warp-native/        # Compression/encryption native (JNI)
├── warp-plugin-loader/ # Chargement et isolation des plugins
└── warp-app/           # Point d'entree (shadowJar)
```

**Justification** : La separation `api/` vs `implementation/` est le pattern le plus unanime parmi tous les projets etudies. Velocity le fait, Krypton le fait, et l'absence de cette separation dans Minestom est consideree comme une faiblesse (les extensions dependent directement des internals).

## 2. SYSTEME DE PAQUETS ET PROTOCOLE

### 2.1 Comment Minestom implemente les paquets

**Sealed interfaces par phase de connexion** :

```
SendablePacket (sealed)
  └── ServerPacket (sealed)
       ├── ServerPacket.Configuration
       ├── ServerPacket.Login
       ├── ServerPacket.Play
       └── ServerPacket.Status
```

Chaque paquet est un **Java record** implementant la sous-interface correspondante :

```java
// Exemple simplifie
public record HandshakePacket(
    int protocolVersion,
    String serverAddress,
    int serverPort,
    int nextState
) implements ClientPreplayPacket { ... }
```

**Principes de design** :
- Les paquets sont **value-based** : pas de dependance a l'identite (pas de `==`, pas de `synchronized`)
- Serialisation/deserialisation via `NetworkBuffer.Type<T>` -- un systeme de codecs type-safe
- `PacketParser` mappe `(ConnectionState, packetId)` -> constructeur de packet
- `PacketReading` lit depuis un `NetworkBuffer` avec gestion du state machine

**Machine a etats du protocole** : `ConnectionState` enum avec les etats `HANDSHAKE -> STATUS | LOGIN -> CONFIGURATION -> PLAY`

### 2.2 Analyse comparative

| Aspect | Minestom | Velocity | Pumpkin (Rust) |
|--------|----------|----------|----------------|
| Type de packet | Record | Classes mutables | Structs + derive macros |
| Hierarchie | Sealed interfaces par phase | StateRegistry par version | Enums par phase |
| Serialisation | NetworkBuffer.Type codecs | Directe dans les classes | Serde-like macros |
| Multi-version | Non (version unique) | Oui (registries par version) | Non |
| Immutabilite | Oui (records) | Non | Oui (ownership) |

### 2.3 Recommandation Warp

**Pattern : Sealed records par phase de connexion**

```java
// warp-protocol
public sealed interface ServerPacket permits
    ServerPacket.Handshake,
    ServerPacket.Status,
    ServerPacket.Login,
    ServerPacket.Configuration,
    ServerPacket.Play {

    void write(NetworkBuffer buffer);

    // Sous-interfaces par phase -- le compilateur garantit l'exhaustivite
    sealed interface Play extends ServerPacket permits
        JoinGamePacket, ChatPacket, KeepAlivePacket, /* ... */ {}
}

public record JoinGamePacket(
    int entityId,
    boolean isHardcore,
    // ...
) implements ServerPacket.Play {
    // Codec statique
    public static final NetworkBuffer.Type<JoinGamePacket> CODEC = ...;
}
```

**Ajout specifique proxy** : Minestom n'a PAS besoin de gerer le multi-version (il ne supporte qu'une version MC). Warp DOIT le faire. Solution : inspiree de Velocity, un `ProtocolRegistry` qui mappe `(protocolVersion, connectionState, packetId)` -> codec.

**Ajout specifique proxy** : Le concept de **RawPacket** (bytes bruts non deserialises) est absent de Minestom mais CRITIQUE pour Warp (blind forwarding). Environ 90% des paquets en PLAY state n'ont pas besoin d'etre deserialises.

```java
public sealed interface ForwardablePacket permits DecodedPacket, RawPacket {
    record DecodedPacket<T extends ServerPacket>(T packet) implements ForwardablePacket {}
    record RawPacket(int packetId, ByteBuf rawData) implements ForwardablePacket {}
}
```

## 3. SYSTEME D'EVENEMENTS (EventNode Tree)

### 3.1 Architecture de l'EventNode

C'est le pattern le plus innovant de Minestom. Le systeme organise les evenements en **arbre hierarchique** ou les evenements descendent du parent vers les enfants.

**Composants d'un noeud** :
- Un filtre de type (`EventFilter<E, H>`) : restreint les evenements acceptes
- Une condition (`BiPredicate`) : filtrage additionnel
- Des listeners
- Des enfants (sous-noeuds)
- Un nom (pour le debug)
- Une priorite

**Types de noeuds** :

```java
// Accepte TOUS les evenements
EventNode<Event> global = EventNode.all("global");

// Filtre par type d'evenement
EventNode<PlayerEvent> playerNode = EventNode.type("players", EventFilter.PLAYER);

// Filtre par valeur (condition sur le handler)
EventNode<PlayerEvent> creativeNode = EventNode.value("creative",
    EventFilter.PLAYER, player -> player.getGameMode() == GameMode.CREATIVE);
```

**Enregistrement de listeners** :

```java
// Simple
node.addListener(PlayerChatEvent.class, event -> { ... });

// Builder avance avec expiration, filtre, etc.
node.addListener(EventListener.builder(EntityTickEvent.class)
    .expireCount(50)                    // Se retire apres 50 appels
    .expireWhen(e -> e.isCancelled())   // Se retire sur condition
    .filter(e -> e.getVelocity() > 0)  // Pre-filtre
    .ignoreCancelled(true)              // Ignore les events annules
    .handler(e -> { ... })
    .build());
```

**Flux d'execution** : L'evenement entre par un noeud, est traite par ses listeners, puis descend dans chaque enfant dont le filtre accepte l'evenement. **Jamais de propagation vers le parent.**

### 3.2 Implementation interne (EventNodeImpl)

**Structures de donnees** :
- `handleMap` : `ConcurrentHashMap<Class, Handle<T>>` -- handlers compiles par type
- `listenerMap` : `ConcurrentHashMap<Class, ListenerEntry<T>>` -- listeners + bindings
- `children` : `CopyOnWriteArraySet<EventNodeImpl<T>>` -- noeuds enfants

**Thread safety** :
- `GLOBAL_CHILD_LOCK` synchronise les modifications structurelles
- `CopyOnWriteArraySet` elimine la contention en lecture
- Champs volatiles pour la visibilite inter-threads
- WeakReferences pour eviter les fuites memoire dans les caches

**Optimisations de performance** :
1. **Compilation lazy** : `Handle.updatedListener()` compile les consumers une fois et cache le resultat
2. **Switch specialise** : `mappedConsumer()` deroule les boucles pour 1-3 filtres
3. **Conversion en array** : Les listeners sont convertis en arrays avant iteration
4. **ListenerHandle direct** : Evite le map lookup via `EventNode#getHandle(Class)`

**Philosophie** : Le systeme est **optimise pour l'appel** (hot path) au detriment de l'enregistrement (cold path). Les modifications structurelles invalident les handles compiles.

### 3.3 Comparaison avec les systemes existants

| Aspect | Minestom EventNode | Velocity EventManager | Bukkit EventHandler |
|--------|--------------------|----------------------|---------------------|
| Structure | Arbre hierarchique | Plat (subscribe/fire) | Plat (priorities) |
| Filtrage | Type + condition + arbre | Aucun natif | Aucun |
| Scope | Naturel via la hierarchie | Global uniquement | Global uniquement |
| Thread | Sync (optimise) | Async (CompletableFuture) | Sync (tick thread) |
| Annulation | `setCancelled()` + `ignoreCancelled` | `ResultedEvent` (vote) | `setCancelled()` |
| Expiration | Oui (count, condition) | Non | Non |
| Performance | O(1) via ListenerHandle | Reflection-based | Reflection-based |

### 3.4 Recommandation Warp : Event Node Tree adapte au proxy

Le concept d'EventNode est **directement applicable** a un proxy, mais le scoping change :

**Serveur MC** : Global -> Instance -> Chunk -> Entity
**Proxy** : Global -> Server(backend) -> Player

```java
// Warp Event Tree
public sealed interface ProxyEvent permits
    ConnectionEvent, ServerEvent, PluginMessageEvent, /* ... */ {}

public sealed interface ConnectionEvent extends ProxyEvent permits
    PreLoginEvent, LoginEvent, DisconnectEvent,
    ServerSwitchEvent, ServerKickEvent {}

// Utilisation
EventNode<ProxyEvent> global = EventNode.all("warp");

// Node scope a un serveur backend
EventNode<ServerEvent> lobbyNode = EventNode.value("lobby",
    EventFilter.SERVER, server -> server.getName().equals("lobby"));

// Node scope a un joueur
EventNode<ConnectionEvent> vipNode = EventNode.value("vip",
    EventFilter.PLAYER, player -> player.hasPermission("vip"));

global.addChild(lobbyNode);
global.addChild(vipNode);
```

**Adaptations proxy** :

1. **Async par defaut** : Contrairement a Minestom (sync, tick-based), un proxy doit gerer les events de maniere asynchrone. Les events comme `PreLoginEvent` doivent supporter `CompletableFuture<Result>` pour ne pas bloquer les threads Netty.

2. **ResultedEvent** (inspire de Velocity) : Les events de decision (login, switch) doivent supporter un systeme de vote/resultat :

```java
public interface ResultedEvent<R extends ResultedEvent.Result> extends ProxyEvent {
    R getResult();
    void setResult(R result);

    sealed interface Result {
        record Allowed() implements Result {}
        record Denied(Component reason) implements Result {}
    }
}
```

3. **Priorite de noeuds** : Essentielle pour qu'un plugin d'auth puisse traiter le login AVANT un plugin de welcome message.

## 4. SYSTEME D'EXTENSIONS (Plugins)

### 4.1 Comment Minestom gere les extensions

**Decouverte** : Scan du dossier `extensions/` pour des JARs contenant `extension.json`

**Manifeste** (`extension.json`) :
```json
{
  "entrypoint": "com.example.MyExtension",
  "name": "MyExtension",
  "version": "1.0.0",
  "dependencies": ["OtherExtension"],
  "externalDependencies": {
    "repositories": [{ "name": "Central", "url": "https://repo1.maven.org/maven2/" }],
    "artifacts": ["com.google.guava:guava:33.0-jre"]
  }
}
```

**Lifecycle** (ordre strict pendant `MinecraftServer#start`) :
1. `preInitialize()` -- appele sur TOUTES les extensions
2. `initialize()` -- appele sur TOUTES les extensions
3. `postInitialize()` -- appele sur TOUTES les extensions
4. `terminate()` -- a l'arret

**ClassLoader** :
- Chaque extension a son propre ClassLoader
- Parent = ClassLoader racine (contient les classes Minestom)
- Isolation totale entre extensions par defaut
- Declarer une dependance dans `extension.json` donne acces a ses classes
- Les libraries externes sont telechargees et cachees dans `extensions/.libs/`

### 4.2 Comparaison des systemes de plugins

| Aspect | Minestom | Velocity | Krypton |
|--------|----------|----------|---------|
| Manifeste | extension.json | @Plugin annotation | Derive de Velocity |
| Decouverte | Scan dossier | AutoService + scan | Scan dossier |
| DI | Aucune | Guice | Derive de Velocity |
| Isolation | ClassLoader par extension | ClassLoader partage | ClassLoader par plugin |
| Dependencies | extension.json | Aucun mecanisme natif | Config-based |
| Externe deps | Maven resolution auto | Shading requis | Config-based |
| Lifecycle | 3 phases (pre/init/post) | ProxyInitializeEvent | Event-based |

### 4.3 Recommandation Warp

**Pattern hybride : le meilleur de Minestom + Velocity**

1. **Manifeste declaratif** (comme Minestom) plutot que annotations :
   - Plus explicite, pas de classpath scanning
   - Permet la resolution de dependencies AVANT le chargement des classes
   - Format : `warp-plugin.json`

```json
{
  "id": "my-plugin",
  "name": "My Plugin",
  "version": "1.0.0",
  "main": "com.example.MyPlugin",
  "api-version": "1.0",
  "dependencies": {
    "required": ["auth-plugin"],
    "optional": ["metrics-plugin"]
  },
  "libraries": ["com.google.guava:guava:33.0-jre"]
}
```

2. **Injection de dependances legere** (inspire de Velocity/Guice, mais sans Guice) :
   - Injection par constructeur des services proxy (ProxyServer, EventManager, Logger, PluginDataFolder)
   - Pas de framework DI complet -- trop lourd pour un proxy

3. **ClassLoader isole** (comme Minestom) :
   - Un ClassLoader par plugin
   - Acces aux classes d'un plugin-dependency via declaration explicite
   - Le ClassLoader parent = API Warp uniquement (PAS l'implementation)

4. **Lifecycle enrichi** (au-dela de Minestom) :

```java
public interface WarpPlugin {
    void onLoad();           // Dependencies resolues, config chargee
    void onEnable();         // Proxy demarre, peut enregistrer events/commands
    void onDisable();        // Arret propre
    void onReload();         // Hot-reload de config (optionnel)
}
```

5. **Resolution Maven automatique** (comme Minestom) :
   - Telecharge et cache les libraries declarees
   - Evite le shading massif que Velocity impose

## 5. MODELE DE THREADS

### 5.1 Minestom : ThreadDispatcher + Acquirable

Minestom utilise un `ThreadDispatcher` qui repartit les ticks par partitions (chunks/instances) sur un pool de threads. L'`Acquirable<T>` API permet l'acces thread-safe entre partitions :

```java
// Thread A veut acceder a une entite tickee dans Thread B
acquirableEntity.sync(entity -> {
    // Execute dans le thread de l'entite, Thread A bloque
    entity.setHealth(20);
});

acquirableEntity.async(entity -> {
    // Planifie pour la fin du tick de l'entite
    entity.teleport(pos);
});
```

**NON APPLICABLE a un proxy** : Un proxy n'a pas de tick loop. Les connexions sont event-driven (I/O Netty).

### 5.2 Velocity : Netty EventLoop

- **Boss EventLoopGroup** : Accepte les connexions entrantes
- **Worker EventLoopGroup** : Gere l'I/O des connexions etablies
- **DNS Thread Pool separe** : Empeche les resolutions DNS de bloquer l'event loop
- **Packet batching** : Flush par lots pour reduire les syscalls

### 5.3 Pumpkin : Async/Sync hybride

- **Tokio** pour l'I/O (reseau, disque)
- **Rayon** pour le CPU-bound (generation de chunks)
- **Channels** pour la communication sans blocage

### 5.4 Recommandation Warp

**Modele : Netty EventLoop + Virtual Threads (Java 21+)**

```
[Netty Boss Group]
    └── Accepte les connexions entrantes

[Netty Worker Group]
    ├── Client EventLoop (decodage/encodage packets client)
    └── Backend EventLoop (decodage/encodage packets backend)

[Virtual Thread Executor]
    ├── Event dispatch (plugins)
    ├── DNS resolution
    └── Operations bloquantes (auth Mojang, requetes DB plugins)

[Packet Forwarding]
    └── Hot path : copie directe ByteBuf client -> backend (zero deserialisation)
```

**Justification** :
- Netty pour l'I/O haute performance (comme Velocity)
- Virtual Threads (Project Loom) au lieu de CompletableFuture chains pour les plugins -- code plus lisible, pas de callback hell
- Le blind forwarding (hot path) reste dans les event loops Netty, JAMAIS delegue a un autre thread
- Les events de plugins qui necessitent du blocking (requete DB, HTTP) tournent sur des virtual threads sans bloquer l'event loop

## 6. CODE GENERATION

### 6.1 Comment Minestom genere le code

Le dossier `code-generators/` produit des classes dans `src/autogenerated/` :
- Constantes de blocs, items, entites, sons, biomes, enchantements, potions
- ~17 000+ variantes d'entites (Pumpkin fait pareil en Rust)
- Generation a partir des fichiers JSON/registries de Minecraft vanilla

### 6.2 Recommandation Warp

**Applicable pour les definitions de paquets** :

Un proxy doit supporter plusieurs versions du protocole MC. Generer les registries de paquets depuis `wiki.vg` ou les data extractors de Minecraft eviterait un maintenance manuelle enorme.

```
code-generators/
├── protocol-extractor/     # Extrait les IDs de paquets par version MC
└── packet-registry-gen/    # Genere les PacketRegistry par version
```

**Generer** :
- `PacketRegistry` par version MC (mapping packetId <-> Class)
- Constantes de packet IDs
- Codecs de serialisation pour les paquets connus du proxy

**NE PAS generer** : le contenu des paquets eux-memes (trop volatile, mieux vaut les coder a la main pour les ~30 paquets que le proxy doit comprendre).

## 7. LECONS DES AUTRES PROJETS

### 7.1 Krypton (Kotlin MC server)

**Ce qu'il emprunte** :
- Events et networking de Minestom
- Plugin loading et permissions de Velocity
- Factory pattern pour les elements d'API (interfaces + factories)

**Lecon pour Warp** : Le pattern factory (API = interfaces, implementation cachee) est excellent. Les plugins ne voient jamais les classes concretes.

```java
// API publique
public interface Player {
    Component displayName();
    void sendMessage(Component message);
    // Pas d'acces aux internals Netty
}

// Implementation interne (package-private)
final class ConnectedPlayer implements Player {
    private final Channel channel;
    // ...
}
```

### 7.2 Pumpkin (Rust MC server)

**Patterns transposables** :

1. **ClientPlatform enum** : Abstraction unifiee Java/Bedrock. Pour Warp, on pourrait avoir une abstraction `BackendConnection` qui cache si le backend est legacy (BungeeCord protocol) ou moderne (Velocity modern forwarding).

2. **Plugins blocking vs non-blocking** : Les handlers de plugins sont soit blocking (acces mutable, sequentiel, peuvent annuler) soit non-blocking (concurrent, lecture seule). Applicable directement a Warp pour distinguer les event listeners qui modifient l'event de ceux qui observent.

3. **Build-time codegen** : Separation stricte entre donnees immutables (registries) et etat mutable (monde). Pour Warp : les definitions de paquets sont immutables, l'etat de connexion est mutable.

4. **Lock-free structures** : ArcSwap au lieu de RwLock. En Java, equivalent = `AtomicReference` + immutable snapshots ou `StampedLock` pour la player registry.

### 7.3 Velocity (Proxy incumbent)

**Forces a conserver** :
- Separation API/Proxy/Native
- Support multi-version via `ProtocolVersion` + `StateRegistry`
- Native compression (libdeflate) et encryption (OpenSSL)
- Rate limiting (Caffeine caches)

**Faiblesses a corriger dans Warp** (cf. `consolidated-proxy-research.md`) :
- Pas de blind forwarding (decompress/recompress tout)
- Pas de drain natif
- Race conditions dans les events de connexion
- CompletableFuture chains complexes (remplacables par virtual threads)
- Pas de hot-reload de plugins

## 8. TABLEAU RECAPITULATIF : PATTERNS -> WARP

| # | Pattern | Source | Applicable | Adaptation Warp |
|---|---------|--------|------------|-----------------|
| 1 | Packets = records immutables | Minestom | OUI | Records + sealed interfaces par phase. Ajouter RawPacket pour blind forwarding |
| 2 | Sealed interface par ConnectionState | Minestom | OUI | Meme pattern, le compilateur force l'exhaustivite des switch |
| 3 | NetworkBuffer.Type codecs | Minestom | PARTIEL | Reprendre le concept, mais la majorite des paquets ne sont pas decodes |
| 4 | EventNode tree hierarchique | Minestom | OUI | Arbre : Global -> Server -> Player. Ajouter async + ResultedEvent |
| 5 | ListenerHandle (O(1) dispatch) | Minestom | OUI | Meme optimisation : pre-compiler les consumers, cacher dans un handle |
| 6 | Listener builder (expiration, filtre) | Minestom | OUI | Utile pour les plugins temporaires (mini-jeux, events) |
| 7 | Extension ClassLoader isole | Minestom | OUI | Un ClassLoader par plugin, parent = API uniquement |
| 8 | Maven dependency resolution auto | Minestom | OUI | Evite le shading, telecharge et cache dans plugins/.libs/ |
| 9 | Manifeste declaratif (extension.json) | Minestom | OUI | warp-plugin.json avec dependencies required/optional |
| 10 | Multi-module API/Impl | Velocity, Krypton | OUI | warp-api / warp-proxy / warp-protocol / warp-native |
| 11 | ProtocolVersion + StateRegistry | Velocity | OUI | Indispensable pour le multi-version |
| 12 | Native compression/encryption | Velocity | OUI | libdeflate + OpenSSL via JNI |
| 13 | Factory pattern (API = interfaces) | Krypton | OUI | Les plugins ne voient jamais les classes concretes |
| 14 | Blocking vs non-blocking listeners | Pumpkin | OUI | Listeners read-only (concurrent) vs mutating (sequentiel) |
| 15 | Build-time codegen pour registries | Minestom, Pumpkin | PARTIEL | Generer les PacketRegistry par version, pas les paquets eux-memes |
| 16 | Virtual Threads pour plugins | Nouveau | OUI | Remplace les CompletableFuture chains de Velocity |
| 17 | Acquirable API | Minestom | NON | Pas de tick loop dans un proxy |
| 18 | ThreadDispatcher par partition | Minestom | NON | Pas de chunks/instances dans un proxy |
| 19 | CopyOnWriteArraySet pour children | Minestom | OUI | Meme pattern pour l'arbre d'events (lectures >> ecritures) |
| 20 | Volatile + WeakRef pour caches | Minestom | OUI | Nettoyage automatique des mapped nodes orphelins |

## 9. PLAN D'ACTION RECOMMANDE

### Phase 1 : Fondations (semaine 1-2)
1. Structure multi-module Gradle (`warp-api`, `warp-protocol`, `warp-proxy`, `warp-app`)
2. `ConnectionState` enum + machine a etats stricte
3. `ServerPacket` / `ClientPacket` sealed interfaces par phase
4. Premiers paquets en records : Handshake, StatusRequest/Response, LoginStart/Success
5. `NetworkBuffer` avec codecs type-safe

### Phase 2 : Networking (semaine 3-4)
6. Pipeline Netty : Boss/Worker EventLoopGroups
7. `RawPacket` pour le blind forwarding (hot path)
8. Compression/decompression native (libdeflate)
9. Encryption (OpenSSL optionnel, Java fallback)
10. `ProtocolVersion` + `PacketRegistry` par version

### Phase 3 : Event System (semaine 5-6)
11. `EventNode<T>` avec filtrage hierarchique
12. `EventFilter` pour le scoping (Global/Server/Player)
13. `ResultedEvent` pour les decisions (login, switch)
14. `ListenerHandle` pour le dispatch O(1)
15. Support async via virtual threads

### Phase 4 : Plugin System (semaine 7-8)
16. `warp-plugin.json` manifeste
17. ClassLoader isole par plugin
18. Resolution Maven des libraries externes
19. Injection des services proxy par constructeur
20. Lifecycle : load -> enable -> disable -> reload
