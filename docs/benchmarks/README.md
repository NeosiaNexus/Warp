# Macro benchmark: how to reproduce, and how results are published

This document covers the macro (whole-proxy) benchmark in [`bench/`](../../bench/README.md): how to
run it, the hardware it needs to produce credible numbers, how it stays fair, what other people have
published and where those attempts fell short, and how Warp's results are published. For the
micro-benchmarks (JMH, per-packet ns/op and B/op) and the four-layer measurement strategy, see
[`docs/research/benchmark-methodology.md`](../research/benchmark-methodology.md). This harness is
layer 3, the macro layer: the proxy is a black box, measured from the outside.

## Running it

```bash
bench/run.sh --smoke     # a couple of minutes, one proxy, a handful of bots: proves the harness works
bench/run.sh             # the full run
bench/run.sh --report-only bench/results/<date>   # rebuild the report of an earlier run
```

The full run, per proxy: boots the backends (the stub backend for the idle scenario, three Paper
servers configured for that proxy's forwarding, and a forwarding-free Paper clone for the latency
baseline), then, for each scenario, launches a fresh proxy process, confirms its natives from the
start-up log, samples it once a second while the load workers drive it, and stops it. Proxies run in
a shuffled order. After each proxy the harness writes that proxy's metrics (`metrics/<proxy>.json`),
its raw samples (`csv/<proxy>.csv`) and the report so far, so a run that is killed keeps the tables
of every proxy that finished; `--report-only` rebuilds the report from those files. Everything
downloaded is verified against the SHA-256 in [`bench/versions.json`](../../bench/versions.json).

Options of note: `--proxies` to pick a subset, `--scenarios` likewise, `--warp-jar` to benchmark a
locally built Warp, `--set scenario.key=value` to override one size of the profile (recorded in the
report), `--no-pin` to turn off CPU pinning, `--out` to choose the results directory. `--load-host`
is reserved for a second load-generation machine; single-machine mode is the default.

The host needs a file-descriptor limit above twice the largest idle level (`ulimit -n`), and, when
`net.ipv4.ip_local_port_range` has been widened to cover the harness's listening ports, those ports
reserved (`sysctl -w net.ipv4.ip_local_reserved_ports=25565,25700-25720`): otherwise an outgoing
connection can take the port a backend is about to listen on. The harness checks this and refuses
to start with the exact command to run.

## Topology: who runs where

One machine, three groups of cores, planned from the core count (`cpuPlan` in `bench/src/env.js`)
and printed at the start of the run and in the report:

| Group | Share of the cores | What runs there |
|---|---|---|
| Proxy | a quarter (at least 2) | the proxy under test, alone |
| Backends | about half | the Paper servers and the stub backend |
| Load | a quarter (at least 2) | one load worker process per core, the last core for the latency probe alone, and the harness itself |

That is 4 / 8 / 4 on 16 cores, 8 / 16 / 8 on 32 and 12 / 24 / 12 on 48. No core is in two groups,
so nothing shares a core with the proxy. Below 6 cores nothing is pinned and the report says so.

The load is generated by separate worker processes (`bench/src/worker.js`), never by the
orchestrating process: one Node.js thread cannot drive hundreds of connections and time them
honestly. Each worker reports how late its event loop ran, and a late generator invalidates the
measurement (see the validity gate).

## The backends are never the bottleneck, or the result is rejected

The first rented run of this harness produced numbers that described the backends and the load
generator, not the proxies (see "What the first rented run got wrong" below). The design that
replaced it:

- **Idle connections use a stub backend** (`bench/src/stubbackend.js`), not Paper. A real server
  cannot hold thousands of players that cost nothing: Paper started refusing logins around 870
  players standing in one lobby, and those players see each other, so the proxy forwards a stream of
  entity packets and the connections are not idle (Warp showed 45% CPU at 500 "idle" connections).
  The stub speaks just enough of protocol 769 to bring a player to the PLAY state through each
  proxy's forwarding (Velocity modern forwarding with the HMAC verified, BungeeCord legacy
  forwarding, or none), sets the same compression threshold as Paper, sends one Join Game, then one
  keep-alive every 15 seconds, the vanilla cadence, and nothing else. It sends no registry data:
  only the harness's raw client connects to it. What the scenario measures is therefore exactly "a
  connection in PLAY at rest": memory, file descriptors and the CPU of keep-alives.
- **Traffic, latency, switch and storm use real Paper**, tuned so a player costs it little, the
  same for every proxy: a flat world, no mobs, view distance 6, no player-data saving
  (`players.disable-saving`), and a player tracking range of 32 blocks instead of Paper's 128, so
  that a player is sent the crowd around it and not every player of the server (the cost of tracking
  grows with the square of a collocated crowd and saturates the server's main thread long before a
  proxy). Each backend is pinned to the backend cores.
- **Traffic bots are raw movers**, not full bot clients: each walks back and forth along its own
  line at sprint speed (5.6 blocks/s, one position packet per tick), which makes the backend stream
  chunks to it for the whole window, next to the movement of the players around it. A mover parses
  only the few small packets it must answer and drops the rest, so a load worker carries hundreds of
  them without lagging. The flat world compresses very well, so the stream is light in bytes for
  the number of chunks it carries; the report gives both the bytes the proxy wrote and the bytes the
  clients received.
- **Switch bots are full mineflayer clients** (they run `/server` and parse every packet), and each
  rests between two switches: the pause sets the offered switch rate so that the backends, for which
  every switch is a full login plus a view distance of chunks, keep their tick rate.

## The validity gate

Every scenario records the offered and the achieved load, the health of the backends, the
saturation of the load generators and whether the proxy engaged a protection, and
`bench/src/validity.js` turns that into a verdict. A measurement that fails is printed as
**INVALID** with its reasons, and its figures are withheld from the tables, the charts and the
memory slopes (they stay in `metrics/<proxy>.json` for diagnosis). The thresholds are constants:

| Constant | Value | Meaning |
|---|---|---|
| `minAchievedRatio` | 0.995 | share of the offered connections that must be established before the window and still be there at its end. This is what makes CPU figures comparable: every proxy carried the same number of bots, or its row is invalid. |
| `minBackendTps` | 19 | a Paper backend's ticks per second over the last minute (asked on its console at the end of the window). Any "Can't keep up" warning or error line since the ramp began also invalidates. |
| `maxLoadgenLagP99Ms` | 50 ms | 99th percentile of a load worker's event-loop delay during the window (the histogram's own resolution is 10 ms) |
| `maxStubLagP99Ms` | 50 ms | the same for the stub backend, which also must refuse no login and time out no player |
| `maxDirectP50Ms` | 5 ms | median of the direct (no proxy) round trip of the latency probe: above it, the path itself was loaded and the "added" figure means nothing |
| `maxSwitchFailureRatio` | 0.02 | share of switch attempts that may fail |
| `minStormDelivery` | 0.9 | share of the flood's offered connections the generator must actually have attempted |

A proxy protection that engages (Warp's circuit breaker ejecting a backend, an anti-bot reaction, a
rate limit) also invalidates: the proxy then carried a different load from the others. An INVALID
row is a statement about the machine or the sizes, not about the proxy alone; when one proxy is
INVALID at a level the others hold, the reasons say which side gave way.

## Equivalent protections

The comparison scenarios run every proxy with equivalent protections, which means none, because the
load comes from one loopback address at rates no real player base produces:

- Velocity `login-ratelimit = 0`; Gate connection and login quotas and packet limiter off;
  BungeeCord `connection_throttle: -1`.
- **Warp: `anti-bot.enabled = false` and `anti-bot.verification.offline-mode` / `online-mode =
  "never"`.** Warp is the only proxy here with an anti-bot. On by default, it verifies every unknown
  identity with a probe before the login reaches a backend and its detector treats a benchmark ramp
  as an attack ("Bot attack detected: logins of unknown identities at N/s"), so Warp did work no
  other proxy did and could delay or refuse bots. Off, the start-up log reads `anti-bot off` and no
  anti-bot line follows. Warp's per-address limits (`limits`) exempt loopback by default, which is
  the equivalent of the rate limits turned off above. The rest of `limits` stays at its default,
  in particular the global cap on connections that are not logged in (8192) and the attack signal
  derived from it (half the cap): a benchmark ramp never comes near them, and the gate rejects the
  measurement if they engage.
- Warp's circuit breaker (a backend that refuses three logins in a row is skipped by the balancers)
  stays at its default: it is routing, not flood protection, and it only acts when a backend refuses
  logins. In the first run it fired 516 times because the backend was drowning, and sent Warp's
  players to the other servers, so Warp ended with a different backend distribution from the other
  proxies. The gate now rejects any measurement during which it fires.

The storm scenario is where a proxy's flood protection is legitimately on, as far as one machine
allows. The flood and the genuine player share the loopback address, so every per-address protection
(Velocity's login rate limit, Gate's quotas, BungeeCord's throttle, Warp's per-address limits once
loopback is not exempt) would throttle the genuine player together with the flood, and those stay
off. A protection that is not per address stays on, and only Warp has one: its cap on connections
that are not logged in, with the attack mode it triggers. In the storm it engages (the flood holds
each hostile connection for three seconds, so 5000 connections per second is 15,000 pending, above
the cap of 8192): Warp then refuses the connections over the cap, the genuine player's among them if
it arrives at the wrong moment. The report says so under the storm table: the share of the flood
each proxy accepted, the protection line, and why a player was kept out. A storm with each proxy's
per-address protections on needs a load generator with many source addresses (T1 with `127.x`
aliases, or T2) and is not built yet.

## Memory: what is reported

The JVM proxies run with `-Xms2g -Xmx2g -XX:+AlwaysPreTouch`, the fair choice for throughput (no
heap resizing, no page faults in the measured window), which pins their resident memory near 2.3 GiB
whatever they do. RSS therefore cannot compare them. The harness also reads the **live heap**: after
each measured window (never inside it) it runs `jcmd <pid> GC.run` then `jcmd <pid> GC.heap_info`
and records the heap still in use (`bench/src/heap.js`). For that the JVM proxies run on a full
Temurin JDK instead of a JRE (same HotSpot). Native memory tracking is not enabled (it costs a few
percent), so direct buffers are not broken out; they show in RSS. For the Go proxies the figure to
read is RSS, as before. "Memory per connection" is the slope between the lowest and the highest
valid idle level, not one absolute number, which would mostly show the runtime's fixed cost.

## Hardware tiers (what you may claim)

The methodology document's tiers apply here directly:

| Tier | Setup | What the numbers are good for |
|---|---|---|
| T0 (WSL2 / laptop) | develop and smoke-test the harness | nothing about timing: no CPU isolation, hypervisor noise. The report flags a WSL run. |
| T1 (minimum credible) | one rented bare-metal Linux host, >= 16 physical cores; proxy pinned to isolated cores, bots on the rest; many `127.x` source IPs | CPU-efficiency, capacity per core budget, relative latency. Loopback has no NIC cost. |
| T2 (gold) | two bare-metal hosts on >= 10 GbE; proxy alone on one, load on the other | every headline claim, including absolute latency over a real NIC |

The single-machine design (the default) targets T1. Run it on a dedicated server, not a shared VM or
WSL, for any number you intend to quote.

## How this harness avoids the known pitfalls

Prior MC-proxy numbers are weak for recurring reasons. Each row below is a documented pitfall and
what this harness does about it.

| Pitfall (seen in the wild) | What this harness does |
|---|---|
| **Synthetic or random payloads.** Velocity's maintainer (astei) dismissed a JMH compression benchmark because it compressed random data, which "cannot represent" real traffic ([Velocity #711](https://github.com/PaperMC/Velocity/issues/711)). | Real Paper backends send a real clientbound stream; movers walk and load actual chunks. No synthetic packets in the traffic path. (The idle scenario alone uses a stub backend, because its subject is a connection that carries nothing.) |
| **Coordinated omission.** Closed-loop generators back off during stalls, so latency looks far better than reality (Gil Tene, "How NOT to Measure Latency"). | The latency probe sends at a fixed cadence whatever the previous round did, and a round that starts behind schedule is timed from the moment it should have been sent; it reports p50/p99/max, never a bare mean. |
| **No warm-up / runs too short.** JVM proxies need minutes of JIT warm-up; a 15 s run hides it (TechEmpower critiques). | Every scenario warms up before it measures, repeats, and the per-second CSV shows the ramp so a reader can see the JIT settle. |
| **Single run, best-case cherry-picking.** | Three repetitions per scenario (one in smoke), median reported, raw CSV published, proxies run in shuffled order. |
| **Undeclared memory metric.** Gate's "10 MB" is idle RSS; a JVM's heap is pre-sized. They are not comparable. | RSS is reported as RSS and labelled, next to the JVM's live heap after a forced collection; the exact `-Xmx`, `-Xms` and GC are in the config and fingerprint. Memory per connection is the slope between idle levels. |
| **Asymmetric tuning / hidden natives.** "Velocity's natives weren't loaded" is the first objection to any Velocity comparison. | Identical headline JVM flags for the JVM proxies; the start-up log is parsed to confirm libdeflate and epoll, and a run that cannot confirm them is marked unfair in the report rather than compared. |
| **Comparing different workload classes.** Gate Lite only pipes bytes (no auth, no server switching). | Lite is labelled a reverse-proxy class and never placed head to head with the full proxies; its switch scenario is skipped, not reported as zero. |
| **Loopback inflating connection rates.** | Loopback is used for CPU-bound numbers; the report states that loopback has no NIC or IRQ cost, and T2 (two hosts) is the setup for latency claims. |
| **Idle bots proving nothing.** 500 idle bots can cost a proxy almost nothing. | Idle connections are a deliberate, separate scenario for per-connection memory; the throughput and latency numbers come from moving bots against a real backend whose TPS must stay healthy, which the validity gate enforces. |
| **A saturated backend or load generator read as a proxy result.** | Offered against achieved load, backend tick rate, backend errors and load-generator lag are recorded for every measurement, and a measurement that fails the gate is printed as INVALID, not as a figure. |
| **Latency quantised by the server's tick or the client's timer.** | The probe times the PLAY ping round trip, which the server answers from its network thread, with the monotonic nanosecond clock, from a process and a core of its own. |
| **Measuring the proxy from inside itself.** | Every number comes from the kernel's view in `/proc`, the JVM's heap accounting through `jcmd`, and client-side timing. The proxy's own metrics are never the source. |
| **Bias not disclosed.** | The report states that the authors are Warp developers, and the harness is open for Velocity, Gate and BungeeCord maintainers to send config fixes. |

## Prior art (and why none of it settles the question)

No rigorous, reproducible, cross-proxy Minecraft benchmark has been published. What exists:

- **Velocity** ["Why Velocity"](https://docs.papermc.io/velocity/why-velocity/): libdeflate "twice as
  fast as zlib", "fewer resources than the competition". The only number is a library micro-benchmark,
  not a proxy measurement; no hardware or method. The page itself says it "may be somewhat biased".
- **Velocity [tuning page](https://docs.papermc.io/velocity/tuning/)**: documents the production JVM
  flags and sizing rules of thumb, with no measurement source. We use its flags in an appendix policy
  and the identical-flags policy for the headline.
- **The "disable backend compression" recommendation**: widely repeated, but not found on current
  Velocity docs; only Gate's docs make the "LAN backend, threshold -1" point. The scenario matrix in
  the methodology still includes an uncompressed-backend case, because that is where the folklore
  lives.
- **Gate** ["Why Gate"](https://gate.minekube.com/guide/why): "10MB RAM", "thousands of players". The
  10 MB is idle RSS with no load or config attached. The [Lite blog](https://connect.minekube.com/blog/gate-lite)
  shows two screenshots with no axes, versions or hardware.
- **"8x faster than BungeeCord"**: traced to hosting knowledge-base pages (e.g.
  [pufferfish.host](https://docs.pufferfish.host/general/velocity-vs-waterfall-vs-bungeecord/)), not
  to PaperMC. No baseline, workload or hardware. One hosting blog
  ([xgamingserver](https://xgamingserver.com/blog/bungeecord-vs-velocity/)) states outright that no
  independent benchmark numbers exist.
- **SoulFire blog**, ["Testing Minecraft Proxy Networks"](https://soulfiremc.com/blog/testing-minecraft-proxy-networks):
  "100+ connections per second, switches under 500ms, under 1GB RAM". Vendor blog for its own bot
  tool; no hardware, versions, run count, or how switch time and memory were measured.
- **Infrarust v2** `mc-bench`: the best MC methodology so far (open-loop, HdrHistogram, direct-baseline
  delta), but self-only, on one dev machine, with tiny opaque ping packets and no CPU-efficiency or
  capacity metric.
- **Bot load tools** (SoulFire, mc-bots, LambdaAttack, PureGero's stress test): all measure connection
  success, none produce a latency distribution or a CPU-per-byte figure. A Rust proxy's own README
  (bardiel) notes 500 fake players cost about 8% CPU, a reminder that idle bots measure little.

General load-testing references the harness takes seriously: Gil Tene on coordinated omission (open
loop, intended-time latency, HdrHistogram, full percentile spectrum) and the TechEmpower critiques
(averages are the wrong ranking statistic; runs must be long enough to expose GC; a standardised
client should enforce correct behaviour).

## What the live validation of each adapter found

Every adapter was run end to end in smoke mode on the development machine before the first rented
run, and each one needed a fix that a config-only review would have missed. Keep these in mind when
updating a proxy version:

- **Velocity**: without a `[forced-hosts]` table it fills in its example hosts, which name servers
  that do not exist, and refuses to start. bStats is opted out through `plugins/bStats/config.txt`.
  During a server switch Velocity kicked the bots with "A packet did not decode successfully":
  with `-Dvelocity.packet-decode-logging=true` it named a serverbound id 0x00 in the CONFIG state
  decoded as ClientSettings ("Bad VarInt"). The bot had sent a PLAY packet (a teleport confirmation
  is also 0x00) in the window after acknowledging the configuration re-entry, which a vanilla
  client never does. Warp drops such a packet; Velocity treats it as corrupt. The harness now
  guards every bot so that only configuration-phase packets leave it in that window
  (`guardConfigPhase` in `bench/src/load.js`). This is a bot behaviour, not a Velocity bug.
- **Gate (full and Lite)**: per-/24 connection and login quotas are on by default (burst 10), so a
  load generator on one address gets exactly ten connections in; the configs turn them off. Gate
  logs one line per connection at INFO, by default; that logging cost is part of what it measures.
- **BungeeCord**: boots with the mbed TLS native cipher and epoll confirmed from its log; it logs a
  WARNING per connection reset, which the storm scenario produces by design.
- **Warp**: its compressor and transport lines are logged at DEBUG, so the config raises those two
  loggers to make the natives check possible.

### Switch latency: where the time goes

The scenario reports two numbers per switch, both measured from the `/server` command: the first
chunk of the new backend reaching the bot (proxy hand-off plus backend login) and five more chunks
(the world is arriving). Bots rest between two switches (`switch.pauseMs`), which sets the offered
switch rate.

An earlier version of the harness counted any chunk received after the command, and its first smoke
runs showed a gap that was not real: about 105 ms to five chunks behind Velocity and BungeeCord
against 615 ms behind Warp. A per-packet timeline of the bot explained it. A bot switches again
about 250 ms after its sixth chunk, long before the previous backend has sent its whole view
distance, so that backend is still streaming chunks when the command goes out, and they keep
arriving until the proxy cuts over (about 40 to 60 ms later, behind Warp and Velocity alike). Those were the chunks
being counted. A run reported about 100 ms when most of its switches caught six leftover chunks
and about 500 ms when they did not, which made the median flip between two modes on timing noise
alone; the same harness, re-run, gave Warp 109 / 504 ms and Velocity 102 / 507 ms. The same flaw
counted a `/server` to the server a bot was already on (every third bot's first hop) as a
successful switch.

The harness now counts only chunks that follow the new backend's Join Game, takes arrival times in
the packet listener instead of a 100 ms poll, and never targets the current server. Measured that
way (medians per run, smoke profile, WSL2, five runs per proxy), Warp and Velocity are
indistinguishable: 334 to 405 ms to the first chunk behind Warp and 323 to 393 ms behind Velocity,
570 to 650 ms to the sixth chunk behind both, with the run-to-run spread larger than any
difference between them. The timeline splits the first figure in two: 40 to 60 ms from the command
to the proxy telling the client to reconfigure and 70 to 135 ms to the new backend's Join Game
(the proxy's share, the same on both), then a constant 245 to 260 ms before Paper sends its first
chunk, whatever the proxy. The bot received no chunk batch packet from Paper 1.21.4 in any trace, behind
either proxy, so the client's batch acknowledgements play no part in the pacing. Read the first-chunk
column as hand-off plus backend login, and expect most of it to be the backend.

## Sizes: what one machine holds

The full profile (`bench/src/profiles.js`) was sized on the first rented server, a 16 dedicated
vCPU / 64 GB cloud instance (plan: proxy on 4 cores, backends on 8, 3 load workers and the probe on
4), by raising each load until the gate rejected it:

| Scenario | Full profile | Largest valid on 16 vCPU | What gives way first |
|---|---|---|---|
| Idle | 1000 / 5000 / 10000 connections, 3 reps | 10000 for Warp, Velocity and Gate, zero failures (20000 held for Warp in a one-rep trial; Gate established 80% of 20000 at 400 connections/s) | the proxy's own login rate; the stub and the raw clients were never late |
| Traffic | 300 movers, 3 reps | 300 (Paper at 20 TPS, about 30 ms of its 50 ms tick). 450 kept 20 TPS but logged an overload warning; 600 fell to 13 TPS | Paper's main thread, which is one core whatever the machine: a larger machine does not raise this |
| Latency | 2000 pings at 50/s, 50 background movers | direct median 0.24 to 0.26 ms | nothing |
| Switch | 60 bots, 3 s pause (about 16 switches/s) | 60 (three backends at 20 TPS, 5 to 8 ms ticks, zero failed switches) | the bot workers: their event loop is 35 to 45 ms late at p99 while parsing chunks |
| Storm | 1000 / 5000 / 10000 connections/s | 5000/s. At 10000/s three load workers deliver about 57% against a proxy that accepts every connection | the load workers: 10000/s needs six or more, that is 28 cores or more |

On a 32 or 48 vCPU machine the same profile runs unchanged (`bench/run.sh`); the plan gives 7 or 11
load workers, which lifts the storm limit, and 16 or 24 backend cores. Expect about 40 minutes per
proxy, a little over 3 hours for the five. A higher idle level can be added with
`--set idle.levels=1000,5000,10000,20000` (about 10 more minutes per proxy; both ends of a proxied
connection use a loopback port, so one level cannot exceed about 28,000 with the default port range).

## What the first rented run got wrong

The first full run on a rented 16-core server (2026-11-12) produced a complete report whose numbers
could not be trusted. What was wrong, and what replaced it:

1. **The backends were being deleted under themselves.** Each proxy's working directory was
   `work/<proxy>` and its backends lived in `work/<proxy>/backends/`; launching the proxy wiped its
   working directory after the backends had booted, so every Paper server lost its world and its
   configuration while running: thousands of `Failed to save player data` and `Expected directory,
   got .../world/region`. The proxy now owns `work/<proxy>/proxy` and never touches the backends.
2. **Idle levels were never reached** (850 to 1475 connected of 2000 and 5000 offered, more than
   10,000 failures per proxy) because Paper refused logins around 870 players, and "idle" players in
   one lobby were not idle. The idle scenario now runs against the stub backend.
3. **Warp's anti-bot was on** and treated the ramp as an attack. It is off (see above).
4. **Warp's circuit breaker ejected the lobby** 516 times as the backend refused logins. With the
   backend healthy it does not fire, and the gate rejects a measurement where it does.
5. **Each proxy carried a different number of bots** in traffic (23 to 220 of 300) and switch: all
   the bots ran in the orchestrator's single thread and the backends were saturated. Load now comes
   from pinned worker processes, and the gate requires 99.5% of the offered load.
6. **Latency was that of an overloaded box** (39 to 78 ms direct on loopback) and was quantised:
   the probe was a tab completion, which Paper answers on its main thread at the next tick, timed
   with a millisecond clock from the same thread as a hundred bots. The probe is now the PLAY ping,
   timed in nanoseconds from its own process.
7. **RSS could not compare the JVM proxies** (2.3 GiB each by construction). The live heap is
   measured.
8. **The report was only written at the very end.** It is now rewritten after each proxy and can be
   rebuilt from the files.
9. **Switch times were in seconds** (200 bots switching as fast as they could saturated the
   backends). Bots rest between switches and the gate checks the three backends.
10. The bot library armed a listener per configuration phase for a packet 1.21.4 never sends, which
    flooded the log with `MaxListenersExceededWarning`; the harness drops it when the phase ends.

## Publishing

- Results are written under `bench/results/<date>/` with the report, raw CSVs, the exact configs and
  the host fingerprint. Only the smoke run's output is committed to this repository.
- A cross-proxy comparison is **not** published yet. Warp's compression passthrough and native path
  are still landing; until they do and the run is done on T1 or T2 hardware, the harness is used
  internally to drive the work. This mirrors the methodology document's recommendation.
- When results are published, they will be in a form a skeptic can re-run: pinned versions with
  checksums, full configs, the fingerprint, and the scenarios where Warp loses included.
- The smoke workflow (`.github/workflows/bench-smoke.yml`, weekly and `workflow_dispatch`) runs the
  harness in smoke mode against every proxy, one job each, and fails when a proxy does not launch,
  a scenario throws or no bot gets through, so the harness never rots. A measurement the validity
  gate rejects does not fail the job: a shared CI runner has no cores to pin, and the report says so.

## Updating the pinned versions

Edit [`bench/versions.json`](../../bench/versions.json). For each artifact, fetch it, record its
SHA-256, and update the entry:

- **Velocity**: the Paper fill API, `https://fill.papermc.io/v3/projects/velocity/versions/<ver>/builds/<n>`
  gives the URL and `checksums.sha256`. The pinned default is the latest 3.4.x build.
- **Gate**: the GitHub release's `gate_<ver>_linux_amd64` asset and its `checksums.txt`.
- **BungeeCord**: the SpigotMC Jenkins `lastSuccessfulBuild` artifact. BungeeCord publishes no
  checksum, so compute the SHA-256 yourself and pin it; the download is still verified against that
  pinned hash, and the report notes it is self-computed.
- **Paper backend**: the Paper fill API, like Velocity.
- **Warp**: the release asset on GitHub, or pass `--warp-jar` for a local build.
